# ai-lazy-memory-architecture

Архитектура памяти ИИ-агента с ленивым хешированием. Вместо одного монолитного дампа, который каждый запрос тащит в контекст целиком, память разложена по уровням с жёсткими границами, а тяжёлые данные подгружаются точечно - только когда задача реально до них дошла. По устройству это фон-неймановский стек, переложенный на контекстное окно: регистры, оперативка, внешний диск и контроллер памяти, только вместо железа - уровни промпта

Подробные разборы - в docs/: code.md (путь запроса и хук context по коду), economics.md (математика экономии в токенах), llm-internals.md (prefill/decode, KV-кэш, окно контекста, откуда берётся цена), lazy-hashing.md (формат указателя, хеш, прыжок, GC), alternatives.md (почему не эмбеддинги, не резюме и не миллионное окно), training.md (архитектура обучения без дообучения: слои, ядро, память уроков, навыки, субагенты), core.md (анатомия ядра AGENTS.md: что внутри, что не кладут, точечная правка, триггеры вырезки), memory.md (полная механика памяти: состав, порядок чтения, три триггера записи, сжатие, дубли, границы), contexts.md (слои контекста, жизненный цикл, насыщение, компакшн, множественные контексты), reasoning.md (размышление: разбор задачи/результата/ошибки, планирование против импровизации, стоп-признаки), tools.md (тул-вызов, тултип как инструкция для модели, выбор, ошибки, слои своих тулов), user.md (работа с юзером: приём задачи, когда спрашивать, споры, стоп, тон), systems.md (скрипты и системы: среда диктует правила, песочница против живой системы, блокировки, отладка), sessions.md (несколько сессий: три типа ресурсов, исключения конфликтов, восстановление)

## Уровни

| Уровень | Аналог | Что внутри | Когда грузится |
| --- | --- | --- | --- |
| Контекст сессии | регистры / L1 | минимальный текущий промпт и точечно извлечённые данные | всегда в рабочем окне |
| Горячее ядро | оперативка / RAM | правила, доступы, таймстампы, однострочные указатели, лимит около 50 КБ | целиком до первого тул-колла |
| Ленивый архив refs/ | внешний диск / HDD | дампы, хроника, завершённые проекты | один прыжок по указателю, никогда целиком |
| Плагин-обёртка | контроллер памяти | хук context, автоинжект ядра, поглощение ошибок | на каждый запрос |

Поток данных выглядит так:

```
[запрос пользователя]
        |
        v
[шина: хук context] --- автоинжект ядра ---> [ядро, <= 50 КБ]
        |                                     (правила, статусы, указатели)
        v
[рабочая области ИИ - контекстное окно сессии]
        |
        | задаче нужны старые контексты и логи
        v
[ленивый прыжок по указателю] <--- индекс ---> [refs/README.md]
        |
        v
   [один точечный файл из архива]
```

Ядро инжектится в каждый запрос через хук context, но не целиком как было с монолитом, а только горячие секции (HOT_SECTIONS): хроника и приватные данные в системный промпт не попадают, из архива в рабочее окно уезжает ровно один файл по теме задачи. Внутри ядра раздел секций заканчивается строкой-указателем вида "## Секция - см. refs/file.md (читать при такой-то теме)", а в самом архиве файл несёт обратную ссылку на родительскую задачу - двунаправленные указатели позволяют восстановить контекст в обе стороны

## Ленивое хеширование

Каждый указатель в ядре хранит путь к файлу в архиве и короткий хеш его содержимого (8-12 символов hex). Хеш считается один раз - при записи файла в архив - и дальше не трогается, пока файл не изменят. Пока задача не потребовала старый контекст, архив не читается и не хешируется ни байт: в ядре лежат просто строки. При прыжке хеш проверяется ровно один раз на чтение: совпал - данные актуальны, не совпал - указатель устарел и ядро перечитывает индекс. Вся экономия на этом: никакой работы по хранению и проверке заранее, стоимость проверки равна стоимости прыжка и оплачивается только когда прыжок случился

Указатель - это строка на 60 байт вместо процитированного куска истории в несколько килобайт. Индекс refs/README.md - ровно одно описание на файл, и он тоже грузится лениво, только вместе с прыжком. Без индекса архив превращается в мёртвую зону: указатель без каталога найти нечем

## Экономия

Каждый токен в системном промпте платится на каждом запросе сессии. Монолит в 500 КБ - это порядка 150-200 тысяч токенов, которые уходят в работу на каждый шаг; разложенная память держит ядро до 50 КБ (15-20 тысяч токенов) плюс копеечный индекс, а всё что крупнее ушло в архив и стоит ноль токенов, пока задача не попросила прыжок. Один ленивый прыжок - это один файл на несколько тысяч токенов вместо сотен тысяч на каждом запросе, и за сессию из двадцати запросов разница умножается на двадцать

Отказоустойчивость и безопасность - часть той же схемы. Секреты в ядро не кладутся вообще, они живут в отдельных *_config.json рядом с инструментом и в промпт или логи не попадают. Ошибка чтения ядра глотается try-catch целиком, так что сбой плагина не роняет рабочую сессию

В архиве работает автономный сборщик мусора. Правило двух недель: завершённые задачи и логи старше 14 дней вычищаются из горячего ядра, полный лог уезжает в refs/chronicle.md, а в ядре остаётся ультра-сжатая строка формата [дата]: [заголовок]. Триггер очистки - превышение лимита ядра в 50 КБ, оно же инициирует рефакторинг памяти

## Внедрение

Шаг 0. Базлайн и git-защита: зафиксировать исходный объём монолита, настроить .gitignore (конфиги, сессии, ключи), первичный коммит

Шаг 1. Инициализация архива: создать refs/ и системный индекс refs/README.md

Шаг 2. Распиловка монолита: перенести логи и спецификации в тематические файлы refs/*.md, заменить блоки в ядре однострочными адресами-указателями с хешем

Шаг 3. Интеграция плагина: развернуть скрипт хука context, настроить автоинжект ядра и try-catch, перезапустить среду

Шаг 4. Ссылочная валидация: прогнать глобальный grep по коду и инструкциям, чтобы ни одна ссылка не зависла в воздухе

Шаг 5. Тест метрик: три сценария - простой запрос из ядра >> глубокая работа с подгрузкой одного файла из refs >> извлечение старого инцидента в один прыжок, на каждом замерить потраченные токены
