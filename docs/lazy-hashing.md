# Ленивое хеширование: механика по шагам

Суть схемы в одном предложении: пока задача не потребовала старый контекст, архив не читается ни байтом, а проверка актуальности оплачивается только вместе с прыжком. Ниже - как это устроено на уровне данных и кода: формат указателя, где считается хеш, что происходит при прыжке и почему это дешевле, чем постоянная проверка

## Формат указателя

Указатель живёт в ядре, это строка на 60-100 байт вместо процитированного куска истории в несколько килобайт. Три компонента: путь к файлу в архиве, короткий хеш содержимого (8-12 символов hex) и одна строка-описание, зачем туда лезть

```
- crash_loop.md [a3f9c1d2] - инцидент 2026-10-06, читать при краш-петле
```

Путь говорит куда, хеш - актуален ли файл, описание - стоит ли вообще прыгать. Третий компонент критичен: без него модель вынуждена читать файл, чтобы понять, что он не нужен, и экономия на прыжке съедается впустую

## Где считается хеш

Хеш считается один раз - в момент записи файла в архив - и дальше не трогается, пока файл не изменят. Это ключевое отличие от "постоянной проверки целостности": заранее не считается ничего, потому что заранее неизвестно, какие файлы вообще понадобятся

```
function writeArchive(name, body) {
    // пишет файл и запоминает хеш в индексе
    const hash = shortHash(body)        // sha256, обрезанный до 10 hex-символов
    writeFile("refs/" + name, body)
    index.set(name, { hash, line: describe(body) })
}
```

shortHash - sha256 от содержимого, обрезанный до 8-12 символов. Обрезка не про безопасность (коллизии на 10 hex-символа возможны, но это не криптографическая задача), а про размер строки в ядре. Задача хеша - поймать изменение файла, а не доказать подлинность

Индекс (refs/README.md) хранит строку описания и хеш для каждого файла. Он сам по себе ленивый: грузится только вместе с прыжком, на обычных запросах его никто не читает

## Что происходит при прыжке

Прыжок - это тул-колл чтения файла из архива. Проверка хеша встроена в него и стоит ровно одно чтение файла, которое так или иначе происходит

```
function jump(pointer) {
    // читает файл архива и сверяет с хешем в указателе
    const body = readFile(pointer.path)
    if (shortHash(body) !== pointer.hash) {
        warn("указатель устарел: " + pointer.path)   // файл менялся, ядро перечитать
        refreshIndex()
    }
    return body
}
```

Совпал - данные актуальны, задача работает с ними. Не совпал - файл менялся с момента записи указателя, индекс перечитывается и ядро получает свежую строку. Второй случай редкий и всегда заметный: он срабатывает один раз на чтение, а не крутится в фоне

Стоимость проверки равна стоимости прыжка и оплачивается только когда прыжок случился. Это и есть вся экономия ленивого хеширования: никакой работы по хранению и проверке заранее, ни одного лишнего чтения на обычном запросе

## Почему не наоборот

Альтернатива - проверять хеши всех архивных файлов на каждом запросе (или по таймеру). Такая схема честно ловит рассинхрон сразу, но за это платится постоянно: N файлов x M запросов чтений впустую, плюс фоновый цикл, плюс состояние кэша хешей. В проекте на 17 файлов и 30 запросов за сессию это сотни лишних чтений, которые не дают ни одной битой информации, потому что архив почти не меняется по ходу работы

Ленивая проверка переворачивает соотношение: ноль проверок на обычном запросе, одна проверка на прыжок, и она попутно отвечает на вопрос "не устарел ли указатель". Частота проверок становится равной частоте обращений - ровно там, где информация о актуальности нужна

## Двунаправленные указатели

Из ядра в архив ведёт строка-указатель, из архива обратно в родительскую задачу - ссылка в шапке файла. Восстановление контекста работает в обе стороны: модель, упавшая в архив по касательной, понимает откуда пришла и что за задача её сюда отправила. Обратная ссылка не читается никогда - она нужна, чтобы файл архива был самодостаточным при выборочном чтении

## Сборщик мусора

Архив растёт, и без выгрузки он превращается в монолит задним числом. Правило двух недель: завершённые задачи и логи старше 14 дней вычищаются из горячего ядра, полный текст уезжает в chronicle.md, в ядре остаётся ультра-сжатая строка "дата: заголовок". Триггер очистки - превышение лимита ядра (50 КБ), оно же инициирует рефакторинг памяти

```
function gc(core) {
    // выгружает в архив всё старое при превышении лимита ядра
    if (size(core) <= CORE_LIMIT) return
    for (const section of core) {
        if (section.age > 14_DAYS) archive(section)   // в ядре остаётся строка-адрес
    }
}
```

Сборщик консервативный: он не трогает ничего живого (секции статусов, правила, указатели) и не работает по таймеру, только по триггеру лимита. Запускать его чаще - значит тратить время на пересортировку того, что ещё не надо пересортировывать

## Цена схемы

Честно о цене: ленивое хеширование требует дисциплины. Указатели протухают, если файл архива переименовали (путь в ядре врёт), и ловит это только прыжок. Описание в указателе устаревает - хеш его не покрывает, он следит за телом файла, а не за строкой в ядре. Индекс надо обновлять вручную при каждом добавлении/удалении файла. Все три - не технические, а человеческие издержки, и они окупаются только если архив реально читается точечно, а не "прочитаем всё на всякий случай"
