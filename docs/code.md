# Код: как память попадает в модель

Промпт для модели - не магия, а обычный payload из текста: история сообщений, системные инструкции, описания тулов, результаты прошлых вызовов. Всё это токенизируется в один кусок и уходит в API. Память агента живёт в системных инструкциях и её размер напрямую множится на каждый запрос сессии. Ниже - разбор по коду: из чего собирается запрос, что делает хук context и почему это не раздувается со временем

## Из чего собирается запрос

Каждый запрос модели собирается из кусков: история сообщений (растёт с каждым шагом сессии), системные инструкции (правила проекта, инжекты, стабильная часть), описания доступных тулов, результаты прошлых тул-коллов. Хроника, приватное и старые инциденты сами по себе в системные инструкции не попадают - их надо туда положить руками. Именно это делает хук

```
запрос пользователя
        |
        v
[сборка payload]
  + история сообщений            (растёт с каждым шагом)
  + системные инструкции          (правила проекта)
  + хук context -> event.system   (горячая память, напоминания)
  + описания тулов и их результаты
        |
        v
[токенизация всего в один payload] -> API -> prefill -> ответ
```

## hotMemory - фильтр по секциям

Это ядро всей идеи: один файл на диске, две проекции. Полную читают точечно по теме, горячую - инжектят на каждый запрос

```typescript
// Секции My memory.txt, которые тащим в каждый запрос.
const HOT_SECTIONS = ["Кто и где", "Время", "Где логи", "Известные проблемы", "Скрипты", "Правила"]

// Читает My memory.txt и оставляет только горячие секции.
function hotMemory(projectDir: string): string {
  try {
    const raw = readFileSync(join(projectDir, "My memory.txt"), "utf8")
    const picked: string[] = []
    for (const chunk of raw.split(/\n## /)) {
      const header = chunk.split("\n", 1)[0]
      if (HOT_SECTIONS.some((prefix) => header.startsWith(prefix))) {
        picked.push("## " + chunk.trimEnd())
      }
    }
    return picked.join("\n\n")
  } catch {
    return ""
  }
}
```

Что здесь важно на уровне поведения. readFileSync вызывается на каждый запрос - файл читается заново, поэтому правки памяти подхватываются сразу, без перезапуска сессии. Один syscall стоит микросекунды и ноль токенов, так что дешевле, чем держать в памяти процесса и потом ловить рассинхрон. split по строке "## " - секции это просто markdown-заголовки, никакой структуры выше. Фильтр startsWith по HOT_SECTIONS - белый список: хронология, приватное и прочее тяжёлое в запрос не едет. catch возвращает пустую строку - нет файла, битая кодировка, любая ошибка означает, что запрос уходит без памяти, а не падает. Деградация лучше падения

## Хук context

```typescript
await ctx.session.hook("context", (event) => {
  try {
    const memory = hotMemory(ctx.location.directory)
    if (memory) {
      event.system.push({
        type: "text",
        text: "Рабочая память проекта (горячие секции My memory.txt):\n" + memory,
      })
    }
    event.system.push({
      type: "text",
      text: 'Напоминание: перед "готово" прогони чек-лист StyleCheck ...',
    })
  } catch {
    // память недоступна - просто работаем без неё
  }
})
```

Среда вызывает хук перед каждым запросом к модели. event.system.push добавляет блок в системные инструкции именно этого запроса - и ничего не сохраняет. На следующем шаге список соберётся заново. Это ключевой момент противопутаницы: если бы блоки копились в истории сообщений, за сто шагов сессии память приехала бы сто раз и мы получили бы ровно тот монолит, от которого уходим. Инжект одноразовый на запрос и пересобираемый, поэтому правка файла действует мгновенно и не плодит копии

try/catch вокруг всего - отказоустойчивость. Сломанный плагин (нет диска, битый файл, исключение в парсере) не должен ронять сессию, он просто перестаёт подмешивать память

## Два источника - это вред, одна проекция - норма

Частое решение - держать отдельный файл "горячего" и отдельный полный, синхронизируя их вручную. Через неделю они разойдутся, и модель будет работать с устаревшей копией, которая выглядит актуальной. Тут один My memory.txt: полная проекция это он целиком (читается точечно), горячая это он минус тяжёлые секции (читается всегда). Правишь файл - правятся обе, расхождение конструктивно невозможно

## Ловушки на уровне кода

Фильтр по префиксу заголовка хрупок: переименовал секцию в My memory.txt - она молча выпала из горячего набора, и HOT_SECTIONS надо править в ту же секунду. Это не баг, это цена простого парсера - зато видно глазами в одном месте

Хук тащит память целиком, без оценки актуальности. Секция "Известные проблемы" может нести месяцами устаревший статус - за это отвечает не код, а дисциплина обновления памяти после каждого результата. Код даёт механизм, правило "правь после итога" держит содержимое честным

Порядок блоков в event.system задаёт среда. Если стабильная часть системника оказывается после нестабильной, ломается префиксное кэширование провайдера (см. economics.md) - но это уже вопрос настройки среды, а не памяти

## Почему дешевле читать файл, чем помнить

Альтернатива readFileSync на каждый запрос - кэш в плагине с проверкой mtime. Разница в микросекундах, которые не видит ни один счётчик токенов, зато кэш добавляет состояние, а состояние протухает. Ленивая память одинакова в своей простоте на обоих концах: архив не читается пока не просят, ядро читается целиком потому что оно и есть запрос, а не потому что кто-то решил его закэшировать
